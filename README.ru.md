# Package SDK

Инструменты и библиотека автора **пакетов каталога** — данных, которыми
организация задаёт правила игры: типы задач, правила вывода работы, процессы,
агенты, правила уведомлений, онтологии и скиллы. Вертикаль — пакет без
собственного runtime; интеграция — пакет класса, провайдерские пакеты и код
наблюдателя и скиллов.

Решение: TAI-ADR-0062.

> **Статус: в разработке.** Уже есть `check`, `test`, `plan`, `apply`, `export`,
> `migrate-expr`, `edit` и `sandbox` — команды инструментов, которые компонент
> заменяет, с тем же поведением. `check` без кода ядра — ошибка; `--schema-only`
> проверяет только схему и ссылки. Проверяется и манифест (переменные, диапазоны
> `requires`, онтологии), а `describe` и `docs` выводят предпосылки установки и
> сгенерированные разделы README пакета. Установка — один план: `lock` фиксирует
> источники (коммит и хэш содержимого каждого пакета в `packages.lock`; источник git —
> `https://` без учётных данных в адресе или `git@хост:путь`, `ref` — тег),
> `plan --install … --out plan.json` строит план всех видов (`package-sdk.plan/v1`) без
> единой записи и отвергает версию ядра вне `engines` пакета и незаданную обязательную
> переменную, а `apply --plan plan.json` применяет ровно этот план после «да» человека и
> останавливается с `plan_stale` до первой записи, если стенд разошёлся с планом. Поля,
> которые человек правил в консоли после прошлого применения, сохраняются, если не задан
> `plan --overwrite-console` (`overwrite_console` у `pkg_plan`): флаг входит в план и
> его хэш, а план перечисляет правки консоли, которые перезапишет или сохранит.
> Из кода — `package_sdk.install.lock()`, `plan()` и `apply()`. Автор работает в
> ИИ-ассистенте через `package-sdk mcp` и плагин `package-author` (ниже). Остальное из
> таблицы — с задачами фичи.

## Что будет

| Область | Команды и модули |
|---|---|
| Создание | `package-sdk init`, `package-sdk add <вид> <ключ>`, `package-sdk edit` (правка с сохранением стиля), `package-sdk workflow` (workflow CI по раскладке установки) |
| Проверка | `package-sdk check` — схема, замкнутость ссылок, объявленные переменные, совместимость с ядром |
| Тесты | `package-sdk test` — пирамида тестов; сценарии исполняет код ядра (сервер или песочница в процессе) |
| Установка | `package-sdk lock`, `package-sdk plan --out`, `package-sdk apply --plan` — один план на все виды, источники по пути или тегу git |
| Интеграции | `package_sdk.connector` — среда наблюдателя; `package-sdk image` — образы наблюдателей и хостов скиллов |
| Автор в ИИ-ассистенте | `package-sdk mcp` и плагин `package-author` |

## Тесты пакета

`package-sdk test [пути…]` прогоняет всю пирамиду пакета и печатает один отчёт с
покрытием (`--json` — документом):

1. **check** — схема, замкнутость ссылок, валидаторы ядра; если она не прошла, тесты
   не запускаются;
2. **skills** — контракты скиллов кода интеграции (`integration/src`) против файлов
   `kind: Skill` пакета (`skill-sdk export --check`);
3. **integration** — pytest кода интеграции (`integration/tests`), если он есть;
4. **scenarios** — `tests/*.test.yaml` процессов, правил вывода работы и типов задач;
   исполняет их код ядра: сервер (`--server`, `POST /packages:test`) или песочница в
   процессе (по умолчанию, дополнение `sandbox`).

Песочница строит каталог из объектов всех видов пакета и его `requires`. Процессы
исполняются в памяти. Сценарии правил и типов задач — прикладной код ядра в
транзакции, которая всегда откатывается, поэтому им нужна пустая база PostgreSQL (с
`pg_trgm`): `--database-url` или `PACKAGE_SDK_SANDBOX_DATABASE_URL`. Песочница сама
накатывает на неё схему закреплённого ядра и заводит там свой tenant — под
advisory-блокировкой PostgreSQL. Пишет она только в пустую базу или в ту, что
подготовила сама (схема ядра и её tenant): базу с другими таблицами, чужими
tenant'ами (например, базу стенда) или со схемой ядра без tenant'а песочницы отвергает
до любой записи. Без базы такие
сценарии помечаются `skipped` с находкой `sandbox_database_required`, и прогон не
зелёный. Ступень без предмета (нет кода интеграции) — `skipped`; ступень, которой
нечем исполниться (нет `skill-sdk`, `pytest` или кода ядра), — ошибка.

Пирамида исполняет код проверяемых пакетов. Код интеграции каждого проверяемого
пакета — названных пакетов, а при `--install` или без аргументов всех пакетов
установки, включая `requires` и пакеты из источников git, — импортирует `skill-sdk
export --check`, а его тесты запускает pytest, в подпроцессах текущего Python. То есть
`test --install` исполняет код каждой интеграции установки, кто бы ни опубликовал её
источник git. Зависимости `integration/pyproject.toml` не ставятся — поставьте их в
окружение сами. Подпроцессы получают окружение без секретов: убираются переменные с
именами токенов, ключей (`*API_KEY*`, `*APIKEY*`, `*ACCESS_KEY*`), персональных токенов
(`*_PAT`), `*_AUTH`, паролей и парольных фраз, учёток, `*_PEM`, адресов баз, `CP_*`,
`CONTROL_PLANE_*`, `IAM_*`, `PACKAGE_SDK_*`, любая переменная, значение которой — адрес с
паролем (`схема://пользователь:пароль@хост`, как в `POSTGRES_URL` или `REDIS_URL`) или
строка подключения с `AccountKey=`, `Password=` или `Pwd=`, и `SSH_AUTH_SOCK`,
`KUBECONFIG`, `DOCKER_AUTH_CONFIG`. Это не песочница: `HOME`
сохраняется, и файлы учётных данных в нём (`~/.aws`, `~/.ssh`, `~/.docker/config.json`,
`~/.netrc` и подобные) этому коду доступны. Проверяйте только пакеты, чьему коду
доверяете.

## Экраны пакета

Экран пакета — описание, а не код (TAI-ADR-0066, CP-ADR-0080): вид `View` (`views/`)
называет источник — экземпляры процесса, задачи типа, записи базы знаний — и
раскладывает блоки закрытого набора версии 1 (`table`, `list`, `board`, `header`,
`fields`, `timeline`, `steps`, `artifacts`, `related`, `metrics`, `chart`, `invoke`,
`component`) с форматами значений; компонент `Component` (`components/`) — повторяемая
часть экрана из тех же блоков, которую ядро встраивает в каждый вид, который его
называет. Поле `code` отвергается. Форма — `schema/v1/view.schema.json`, побайтная копия
схемы ядра (`$defs.viewSpec`, `$defs.componentSpec`).

Все строки, которые видит человек, — ключи словарей пакета: `package.yaml` объявляет
`locales: [en, ru]` и `defaultLocale`, на каждый язык — `i18n/<locale>.yaml`, плоское
отображение ключ → текст с подстановками ICU (`{count, plural, one {# счёт} other
{# счетов}}`). Колонка без `label` подписана ключом `<пакет>.fields.<путь>`.

`check` находит, с файлом и JSON Pointer места: ключа нет в словаре объявленного языка
(`missing_message`), словарь необъявленного языка (`undeclared_locale`), неизвестный
блок или формат (`unknown_block`, `unknown_format`), агрегат вне `metrics` и `chart`
(`aggregate_outside_metrics`), `open.view` на несуществующий вид (`unknown_view`),
процесс или тип задачи источника вне пакета и его `requires` (`unknown_source`) и
ключ, который не показывает ни один вид (`unused_message`, предупреждение). Пути
данных и выражения CEL проверяет код ядра — тот же, что строит план; если ядро рядом
старше экранов, `check` говорит, что их проверит план. Пакет с экранами уходит в план
ядра вместе со словарями: виды планирует и публикует ядро. Эталон —
`tests/fixtures/screens/packages/invoice-payment`.

## Настройки пакета

`spec.settings` манифеста объявляет значения, которые администратор организации меняет
в живой системе — без новой версии пакета и без плана установки (переменные остаются
для топологии установки). Значения хранит ядро; процессы, правила вывода работы и виды
читают их как `settings.<поле>`.

```yaml
spec:
  settings:
    schema:
      type: object
      required: [refundThreshold]
      properties:
        refundThreshold: {type: integer, minimum: 0, default: 50000}
        escalationRole: {type: string, x-ref: role, default: claims-lead}
    uischema:
      type: VerticalLayout
      elements:
        - {type: Group, label: acme-claims.settings.groups.approval, elements: [
            {type: Control, scope: "#/properties/refundThreshold"},
            {type: Control, scope: "#/properties/escalationRole"}]}
```

- `schema` — закрытое подмножество JSON Schema: `type`, `properties`, `required`, `enum`,
  `minimum`/`maximum`, `minLength`/`maxLength`, `pattern`, `format` (`date`, `uri`,
  `email`, `uuid`), `items`, `minItems`/`maxItems`, `default`, `additionalProperties:
  false` и `x-ref` (`role`, `principal`, `workspace`, `calendar`, `taskType` — значение
  ссылается на объект платформы: id роли, principal или workspace, ключ типа задачи
  или календаря). Корень — объект, вложенность объектов — не глубже 3 уровней (`items`
  массива — тоже уровень, на последнем — только скаляры), свойств у объекта — не
  больше 100. Подмножество — ровно то, что принимает ядро (CP-ADR-0081 п.1–2).
  Прочее — `writeOnly`, `format: password`, `title`, `$ref`, комбинаторы — схема
  отвергает.
- `uischema` (необязательно) — подмножество JSON Forms, которое рисует консоль:
  `VerticalLayout`, `HorizontalLayout`, `Group` (с `label`), `Control` (`scope` —
  `#/properties/…`, `label`) и `Label` (`text`), и правила с эффектами `SHOW`, `HIDE`,
  `ENABLE`, `DISABLE` по условию `{scope, schema}` (в `schema` — ключевые слова поля без
  `x-ref` и `default`, и `const`). `options` у `Control`, `Categorization`,
  `ListWithDetail` и свои renderers отвергаются.
- Подписи — не тексты: `label` и `text` — ключи словарей пакета; подпись поля — ключ
  `<пакет>.settings.<путь>`.

Тест пакета задаёт значения до сценария через `given.settings` (тесты процессов и
правил) и меняет их посреди сценария процесса шагом `settings: {...}`. Значения
заменяют сохранённые; незаданные поля берут `default`.

`package-sdk check` находит то, чего не выразить схемой, с кодами и путями плана ядра
(CP-ADR-0081): `settings_schema_unsupported` (ключевое слово не своего типа, `required`
с полем, которого нет в `properties`, `enum` у `object` или `array`, массив глубже
последнего уровня), `settings_default_missing` (у необязательного поля нет `default`),
`settings_default_invalid` (`default` не проходит своё поле, например
`{type: integer, default: "x"}`), `settings_secret_field` (`writeOnly`,
`format: password`, имя поля, которое ядро считает секретом, — `password`, `secret`,
`token`, `apiKey`, `privateKey`, `credential`, `authorization`, `clientSecret`, а
`secretRef` допустим, — или материал секрета в `default` и `enum`),
`settings_uischema_unsupported` (`scope` не на свойство схемы, второй `Control` на одно
свойство, подпись `Group` не вида `<пакет>.settings.groups.<id>`),
`settings_uischema_uncovered` (предупреждение: поле не правит ни один `Control`) и
`settings_label_missing` (ключа подписи нет в словаре объявленного языка:
`<пакет>.title`, `<пакет>.settings.<путь>` каждого свойства, ключи `uischema`). Чтения
`settings.<путь>` в процессах, правилах вывода работы и видах дают
`settings_ref_unknown` (такого поля настройки не объявляют или пакет их не объявляет) и
`settings_ref_type` (тип поля не подходит месту чтения — объект в сравнении или внутри
текста); путь — путь выражения в его файле. Если код ядра рядом знает настройки,
ссылки проверяет он сам: процессы — `check_process`, правила — `check_settings_refs`
(первое неподходящее чтение правила, как в плане), виды — `check_view`. Без него `check`
проверяет правила сам (все чтения), а в выражениях CEL процессов и видов ловит только
необъявленные поля и говорит, что типы проверит план. Внутри ветки `catch … as:
settings` процесса имя — ошибка, а не настройки: её чтения ссылками не считаются,
остальные чтения процесса проверяются.

Срок можно считать от настроек: число `workdays` или `workhours` у `due` (шага или
процесса целиком) и у его `warnBefore` — число или `{expr: <CEL>}`, неотрицательное
целое, которое ядро вычисляет один раз при входе в шаг (`spec.due` — при старте
экземпляра); дальше срок, его предупреждение и пауза ведут себя как у числа
(CP-ADR-0081, амендмент 2026-10-03, Г1–Г4):

```yaml
due: {workdays: {expr: settings.reviewDueWorkdays}, warnBefore: {workhours: 4}}
due: {workdays: 5, warnBefore: {workdays: {expr: settings.warnDays}}}
```

Чтения `settings.<путь>` там `check` проверяет, как любые другие: путь находки — путь
выражения, например `/spec/stages/0/steps/0/human/due/workdays/expr`, поле не
`integer` (`number`, `string`, объект) — `settings_ref_type`. Если ядро рядом считает
такие сроки, проверка — его; со старым ядром или без ядра `check` сам типизирует
выражение из одного чтения (`settings.reviewDueWorkdays`), а типы составного оставляет
плану с предупреждением. Песочница со старым ядром отвергает такой `due` как нарушение
схемы. В тесте `given.settings` и шаг `settings` до входа в шаг меняют его срок, после
входа — нет.

`package-sdk sandbox` передаёт ядру `given.settings` и шаги `settings`, ядро проверяет
их по схеме из файлов пакета, как сохранение администратора. Организации у песочницы
нет: `x-ref` на тип задачи или календарь должен называть объект пакета и его
`requires`, а id ролей, principal'ов и workspace считаются существующими. С ядром
старше настроек пакет, который их читает, или тест, который их сохраняет, — находка
`sandbox_settings_unsupported`, а не молчаливый зелёный прогон. `package-sdk describe`
показывает настройки рядом с переменными установки: путь, тип, `default`,
обязательность и на что ссылается `x-ref`. Эталон —
`tests/fixtures/settings/packages/claims-intake`.

## Типы подключений

`ConnectionType` (`connection-types/`) описывает, что нужно, чтобы подключить систему
такого вида (CP-ADR-0079 §2): способы подключения (`auth`: `oauth2`, `token`), поток
OAuth 2 (`oauth2`: `authorizeUrl`, `tokenUrlTemplate`, `accountParam`, `authStyle`,
`scopes`), поле учётки в форме ввода ключа (`accountField`: `title`, `pattern`), JSON
Schema несекретных настроек подключения (`settingsSchema`) и ключ подключения по
умолчанию (`defaultKey`). Значений секретов тип не несёт — их вводит администратор в
консоли. Агент называет подключения, к материалу доступа которых ему можно обращаться,
в `Agent.spec.connections` (до 20 ключей). Пример — в `README.md`.

Версии — как у `Skill`: `spec.version` задаёт пакет, объект называется
`ConnectionType/<ключ>@<версия>`, опубликованная версия неизменяема — изменённый файл с
той же версией отвергается до записи, поднимите `spec.version`. План публикует
недостающую версию, возвращает `deprecated` в `active` и не трогает версию, которую
администратор отключил (`disabled`); `retire: {ConnectionType: [<ключ>]}` переводит все
активные версии в `deprecated` (новых подключений нет, существующие работают).

`check` без стенда находит: `oauth2` без своего блока, `token` или `{account}` в
`tokenUrlTemplate` без `accountField` (и `{account}` без `accountParam`), любой
плейсхолдер, кроме `{account}`, хост адреса обмена, который не внешнее DNS-имя (одна
метка, IP-литерал, порт или userinfo), некомпилируемый шаблон учётки, свойство настроек
с именем секрета, материал доступа в строках типа и — предупреждением — ключ в
`Agent.spec.connections`, который не `defaultKey` ни одного типа пакета и его
`requires`. С ядром рядом, которое старше подключений, `check` говорит, что
`connections` агента проверит стенд, а песочница не передаёт типы подключений в
тестируемый пакет.

## Автор в ИИ-ассистенте

`package-sdk mcp` — MCP-сервер по stdio (дополнение `mcp`) с инструментами автора пакетов
поверх тех же функций, что у CLI:

| Инструмент | То же, что |
|---|---|
| `pkg_check(path \| install, server?, workspace_id?, schema_only?)` | `package-sdk check --json` |
| `pkg_test(path \| install, tests?, server?, workspace_id?)` | `package-sdk test --json` |
| `pkg_describe(path, env_example?)` | `package-sdk describe --json` |
| `pkg_edit(operation, options, dry_run?)` | `package-sdk edit <операция> …` |
| `pkg_plan(server?, install \| path, out?, workspace_id?, replay_limit?, overwrite_console?)` | `package-sdk plan --out` |
| `pkg_apply(plan_file, plan_hash)` | `package-sdk apply --plan` |

`pkg_plan` сохраняет план файлом (по умолчанию `.package-sdk/plan.json`; для каталога
одного пакета рядом с планом пишется его установка) и возвращает `planHash`. `pkg_apply`
применяет только этот сохранённый план и только по его хэшу: вызов без `plan_hash` или с
хэшем другого плана отвергается до чтения стенда, а стенд, изменившийся после плана, даёт
`plan_stale` до первой записи. Подтверждение человека берёт хост: хук плагина спрашивает его
перед каждым `pkg_apply`. Учётка стенда — та же, что у оператора: `CP_TOKEN` или credential,
который находит `control-plane-client` (`resolve_credential`). Access token живёт минуты, а
план или применение — дольше, поэтому токен credential берётся перед каждым запросом и
обновляется, когда истекает; на `401 invalid_credentials` — один повтор с обновлённым
токеном. `CP_TOKEN` и `NOTIFY_TOKEN` — выбор человека, они берутся как есть.

Сервер говорит только со стендами из `PACKAGE_SDK_SERVERS` своего окружения (другой адрес —
`server_not_allowed` до запроса токена) и работает внутри корня сессии (`PACKAGE_SDK_ROOT`,
корень `file://` клиента или рабочий каталог): правит только внутри него, планы пишет только
в `<корень>/.package-sdk/` и файл, который не план, не перезаписывает. План читается один раз,
и применяется ровно прочитанный документ.

Плагин Claude Code `package-author` (`plugin/package-author`, marketplace `package-sdk` в
`.claude-plugin/` этого репозитория) приносит сервер, шестнадцать скиллов на весь цикл
пакета — типы задач, правила, процессы, агенты, интеграции, онтологии, уведомления, тесты,
выпуск и установку — и хук `confirm_apply.py` на `pkg_apply`:

```bash
uv tool install "package-sdk[mcp,sandbox,skills] @ git+https://github.com/<org>/package-sdk@<тег>"
claude plugin marketplace add <org>/package-sdk
```

## Пример

[examples/claims](examples/claims/README.md) — претензии клиентов целиком: пакет с процессом,
правилом вывода работы, правилом уведомления, онтологией, агентами с образами и кодом
интеграции со службой поддержки (наблюдатель и скиллы), демонстрационный источник
обращений, сценарии и unit-тесты. CI прогоняет всю его пирамиду в песочнице на каждом
изменении; job, который ставит его на стенд открытой поставки и доводит обращение в
источнике до закрытия дела, проверяется на публичном зеркале. Пример — на английском, как и
открытая поставка.

## Кэш источников git

Источники git лежат в `$PACKAGE_SDK_CACHE` (по умолчанию `~/.cache/package-sdk`):
зеркало каждого источника и выгрузки его коммитов. Временные выгрузки, брошенные
упавшим прогоном (`.staging-*`), убираются, когда им больше часа, при каждом обращении
к кэшу этого источника. Выгрузки, которые больше не нужны ни одному lock, убираются
вручную:

```bash
package-sdk cache prune                  # оставить то, на что ссылаются packages.lock под .
package-sdk cache prune --lock deploy/packages.lock --lock other/packages.lock
package-sdk cache prune --all            # весь кэш: выгрузки и зеркала
```

Без `--all` зеркала остаются: выгрузка из зеркала повторяется без сети. Выгрузка,
которую использует установка в другом каталоге, для `prune` ничья — запускайте его там,
где лежат все ваши установки, или передайте их lock-файлы. Если под текущим каталогом нет
ни одного lock-файла (поиск — на шесть уровней вглубь и никогда из домашнего каталога),
`prune` отказывает, а не удаляет всё; всё — только явно, `--all`. Выгрузка, которую
использовали за последний час, остаётся и без ссылок: её может читать параллельный
`lock` или `plan`. У `--all` такой отсрочки нет: он удаляет и свежие выгрузки, поэтому
параллельный `lock`, `plan` или `test` сорвётся с отказом «выгрузка удалена во время
чтения, повторите» — запускайте `--all`, когда кэшем больше никто не пользуется.
Символические ссылки в кэше не обходятся и не удаляются.

## Секреты наблюдателя

Наблюдатель (`package_sdk.connector`) берёт секреты узла только из файлов:
`ctx.secret(name)` читает `$CONNECTOR_SECRETS_DIR/<имя>` (по умолчанию `/run/secrets`)
при каждом вызове, по канону skill-sdk (`skill_sdk.secrets.read_secret_file`). Образ
наблюдателя ставит только extra `connector`, поэтому правило повторено в
`package_sdk.connector.secrets`, а одна таблица примеров гоняется по обеим реализациям.

- Имя — по шаблону `[a-z0-9][a-z0-9-]{0,62}`; `agent-pat` зарезервировано.
- Нет файла, файл пуст или из одних пробельных символов — «секрета нет»:
  `SecretMissing`, раз в сутки `connector.secret_missing`, цикл пропускается. В
  остальных случаях обрезаются только хвостовые `\r`/`\n`; пробелы непустого значения
  остаются.
- Всё остальное — `SecretRejected` с кодом и причиной канона: имя не по шаблону,
  ссылка или `..` за пределы каталога, путь, подменённый на каждой из трёх попыток, не
  обычный файл, больше 64 КиБ, не UTF-8, нет прав на чтение. Цикл завершается сбоем
  `connector.cycle_failed` с полями `secret`, `code` и `reason`, без значения.

Путь проходится от дескриптора каталога секретов с `O_NOFOLLOW` на каждом компоненте.
Это защита в глубину, а не гарантия: кто может подменять сам путь каталога секретов или
писать в него, управляет секретами.

Что изменилось по сравнению с прежним чтением (`read_text().strip()`, любой `OSError` —
«секрета нет»):

- файл без прав на чтение теперь даёт `cycle_failed` (`secret_unreadable`), а не
  «секрета нет»: наблюдатель, который без секрета работает без токена (selfdev
  `_github_token`), при ошибке прав больше не делает этого молча;
- ведущие пробелы непустого значения сохраняются;
- имена не по шаблону (`EXT_TOKEN`) и `agent-pat` отвергаются.

## Совместимость

Проверки, тесты и песочница SDK идут кодом ядра, поэтому каждый выпуск проверен на
определённых тегах соседних компонентов. Клонируйте их рядом с SDK на этих тегах в
раскладке из манифеста выпуска (ниже) и закрепите те же теги в CI пакета (`CONTROL_PLANE_REF`,
`PLATFORM_AUTH_SDK_REF`, `SKILL_SDK_REF` в workflow, который пишет `init`).

| package-sdk | control-plane | platform-auth-sdk | skill-sdk |
|---|---|---|---|
| 0.1.0 | v0.9.4 | v0.1.1 | v0.1.1 |
| 0.2.0 | v0.10.0 | v0.2.0 | v0.2.0 |

Как заполняется строка:

- **control-plane** — наименьший тег ядра, на API и моделях которого проверен выпуск;
  диапазон `engines`, который `init` пишет пакету, следует тому же minor.
- **platform-auth-sdk** — зависимость ядра, а не SDK: тег из того же выпуска
  платформы, то есть указатель сабмодуля зонтика. Ядро требует лишь
  `platform-auth-sdk>=0.1.0`, номер тега из его `pyproject.toml` не вывести.
- **skill-sdk** — нужен только дополнению `skills`: тег из того же выпуска платформы,
  что и ядро.

Номера тегов появляются в строке, когда теги выпущены; до того в ней записано правило,
а не угаданный номер.

## Раскладка установки

Компоненты ссылаются друг на друга относительными путями (`package-sdk` →
`../../services/control-plane`), поэтому путь между двумя компонентами одинаков везде, где они
собираются вместе: в зонтике, образах, рабочих копиях раннера и CI пакета. Где лежит
каждый компонент — манифест раскладки выпуска `package_sdk/layout.json`: стабильное имя
компонента → путь в дереве установки. Он меняется вместе с path-зависимостями
`pyproject.toml`.

| Компонент | 0.1.x (плоская раскладка) | после переезда в `services/` и `sdk/` |
|---|---|---|
| package-sdk | `package-sdk` | `sdk/package-sdk` |
| control-plane | `control-plane` | `services/control-plane` |
| platform-auth-sdk | `platform-auth-sdk` | `sdk/platform-auth-sdk` |
| skill-sdk | `skill-sdk` | `sdk/skill-sdk` |

Workflow, который пишет `init`, клонирует компоненты в `.platform/` по этому манифесту:
`clone <имя> "$<ИМЯ>_REF"` в плоской раскладке, `clone <имя> <путь> "$<ИМЯ>_REF"` — когда
в путях есть сегменты. Адрес клона — всегда по имени (`$PLATFORM_GIT/<имя>.git`).
Выпуски разных раскладок не смешиваются: ревизии и раскладка workflow — из одной
установки.

Рабочая копия `Agent` следует тому же правилу: `workingCopy.directory`, ключи
`workingCopy.neighbours` и `directory` записи каталога принимают плоское имя
(`control-plane`) или относительный путь из сегментов (`services/control-plane`); `..`,
абсолютные пути, пустые сегменты и обратные слэши отклоняются, а `check` находит запись
каталога, лежащую внутри каталога другой.

Пакет, чей workflow написал прежний `init`, перегенерирует его после обновления
package-sdk:

```bash
package-sdk workflow .          # переписать .github/workflows/package.yml по этой установке
package-sdk workflow . --check  # код 1, если файл отличается; ничего не пишется
```

Команда сохраняет ключ пакета, код интеграции (`integration/` или skill-sdk в прежнем
файле), базу (включена в прежнем файле или нужна сценариям правил и типов задач) и
дописанные к строке `uv tool install` опции `--with`. Прочие ручные правки файла не
сохраняются — посмотрите diff перед коммитом. На плоской раскладке результат — прежний
файл байт в байт. Ревизия, которой эта установка не знает, выводится предупреждением, и
job останавливается на ней, пока её не зададут.

## Разработка

Из корневого репозитория, где соседи — сабмодули:

```bash
uv sync
uv run pytest
uv run ruff check . && uv run ruff format --check .
```

Заметки:

- `uv.lock` разрешает дополнения по `../../services/control-plane` корневого
  репозитория, то есть следует ревизии ядра, закреплённой в нём; после сдвига
  указателя обновляется `uv lock`.
- Тесты перенесённых инструментов идут на обезличенном снимке пакетов и установок
  `tests/fixtures/umbrella`. `PACKAGE_SDK_UMBRELLA=<umbrella>` запускает их на живом
  дереве.
- `tests/test_pyramid.py` прогоняет сценарии `tests/fixtures/pyramid` обоими
  исполнителями и сравнивает отчёты (`package_sdk.testing.divergence`). Сравнению нужен
  PostgreSQL: при `PACKAGE_SDK_SANDBOX_DATABASE_URL` (сервер, где тесту можно создать и
  удалить базу) сервер — приложение ядра в процессе на той же базе; при
  `PACKAGE_SDK_TEST_SERVER` (и `CP_TOKEN`) — ещё и живой стенд. Без них эти два теста
  пропускаются.
