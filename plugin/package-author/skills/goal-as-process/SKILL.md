# Цель как процесс

Отдельной сущности «цель» нет: желаемое состояние
описывается процессом. Этот скилл решает, какой формы процесс нужен, и даёт
образец процесса-сверки. Дальше работа идёт обычным путём: тесты
(`write-tests-first`) → описание (`author-package`) → проверка
(`validate-and-fix`) → план и согласие (`simulate-and-plan`).

## Правило плагина

Применение на стенде — только после показа плана и явного «да» человека
(`simulate-and-plan`). Экземпляр постоянной цели заводит человек или установка
пакета явным стартом (право `processes.operate`). Агент его сам не заводит.

## Выбор формы

| Что говорит человек | Форма |
|---|---|
| «согласовать эту закупку», «закрыть эту претензию» | цель дела = **экземпляр процесса с исходом** (`complete: {outcome: …}`); отдельного процесса-цели не нужно |
| «все претензии закрыты в срок», «сервис соответствует требованиям» — состояние, которое надо держать | **процесс-сверка без `complete`**: один экземпляр, реакции на наблюдения, вехи, задачи на восстановление |
| «за квартал: 100 претензий, 90 % закрыты в срок» — итог по многим делам | **сводный процесс**: слушает `process.completed` других процессов и считает итог в своих данных |
| цель из подцелей | вложенные процессы (`call: {process: …}`) и связи дел в памяти |

`goalId` в новых описаниях не используй: поле выводится из ядра.

## Порядок для процесса-сверки

1. **Сформулируй состояние** проверяемо: что наблюдаем, при каком условии
   состояние «достигнуто», при каком — «нарушено». Примеры: «нет претензии с
   просрочкой оплаты больше 0 рабочих дней», «нет задачи расхождения с ADR
   старше 5 дней».
2. **Источник наблюдений.** Какие события и наблюдения меняют состояние
   (`claim.resolved`, `process.completed`, наблюдение коннектора, событие
   ядра). Если источника нет, сначала нужен коннектор или правило. Скажи
   об этом человеку.
3. **Один экземпляр.** `start.key` — константа (`"'claims-on-time'"`) или
   ключ области (workspace, квартал). Повтор стартового события с тем же ключом
   попадает в существующий экземпляр (`correlate`), нового не заводит.
4. **Данные экземпляра** — сводка состояния: счётчики, списки нарушителей,
   дата последней сверки.
5. **Реакции** в `onEvent` (или `listen` в стадии с `repeatable: true`):
   обновить данные `set`, при нарушении — задача на восстановление (`human`
   с назначением владельцу или ответственной роли), при восстановлении —
   закрыть или отметить.
6. **Вехи** стадии: `milestones: [{id: on-track, when: <CEL>}, {id:
   breached, when: <CEL>}]`. Веха снимается и достигается снова, когда
   меняются данные.
7. **Без `complete`.** Проверка может сообщить `dead_end` или «процесс не
   завершается». Для процесса-сверки это ожидаемо. Объясни это человеку и не
   добавляй фиктивный исход.
8. **Периодическая сверка**, если событий мало: таймер стадии с `wait` или
   `timers` → `call` скилла проверки → `set` сводки.
9. **Память:** `memory.case` с ключом цели. Дела, работающие на цель,
   связываются с ней проекцией (связь `involves` онтологии `process-knowledge`).
   Вопрос «какие дела работали на цель и чем кончились» решается обходом
   графа.

## Образец (фрагмент)

```yaml
spec:
  version: 1
  displayName: Претензии закрываются в срок
  identity: {agent: claims-process}
  owner: [{role: claims-lead}]
  calendar: workdays
  data:
    type: object
    properties:
      overdue: {type: array, items: {type: string}}
      checkedAt: {type: string, format: date-time}
  start:
    on: {event: process.completed, where: "event.payload.definitionKey == 'claim'"}
    key: "'claims-on-time'"
  correlate:
    - on: {observation: claim.overdue}
      key: "'claims-on-time'"
      do:
        - {id: mark-overdue, set: {overdue: "data.overdue + [event.payload.claim]"}}
        - id: restore
          human:
            taskType: claim-overdue
            title: "'Просрочен ответ на претензию ' + event.payload.claim"
            assign: [{role: claims-officer}]
            due: P1D
  stages:
    - id: watch
      repeatable: true
      milestones:
        - {id: on-track, when: "size(data.overdue) == 0"}
        - {id: breached, when: "size(data.overdue) > 0"}
      steps:
        - id: wait-signal
          listen:
            any:
              - on: {observation: claim.resolved}
                do: [{id: unmark, set: {overdue: "data.overdue.filter(i, i != event.payload.claim)"}}]
```

Это фрагмент для формы, а не готовый пакет: событие старта, наблюдения и тип
задачи подставь из своего домена и проверь `validate-and-fix`.

## Тесты для процесса-сверки

- нарушение → веха `breached` и задача на восстановление;
- восстановление → веха `on-track`, задача не дублируется при повторе;
- повтор стартового события → тот же экземпляр (`expect.events` без второго
  старта);
- статус остаётся `running` после всех событий.

## Чек-лист

- [ ] Форма выбрана по таблице и объяснена человеку.
- [ ] «Достигнуто» и «нарушено» выражены CEL над данными экземпляра.
- [ ] Ключ экземпляра даёт ровно один экземпляр на область цели.
- [ ] Нет `complete` у постоянной цели; есть у цели дела.
- [ ] Задачи на восстановление не дублируются при повторных наблюдениях.
- [ ] У процесса есть `owner`.

## Частые ошибки

- Заводить отдельный «процесс-цель» для цели одного дела: это исход
  экземпляра.
- Считать «сейчас» внутри сверки через `now()`: времени нет, есть
  `event.time`, `instance.clock` и таймеры.
- Ставить `complete`, когда состояние достигнуто: цель снова нарушится, а
  экземпляра уже нет.
- Ссылаться на `goalId`.
