# Процесс по регламенту из базы знаний

Регламент — источник требований. Процесс ссылается на его пункты
(`governedBy`), тесты проверяют проверяемые требования, а план ядра показывает,
какие пункты процессом не покрыты.

## Правило плагина

Ничего не применяется на стенде без явного «да» человека на показанный план
(скилл `simulate-and-plan`). Этот скилл читает базу знаний и пишет файлы пакета
в репозитории. На стенд он не пишет.

## Порядок

1. **Найди регламент.** Вызови `cp_recall` с `query` — названием, как его
   назвал человек, и `kinds: ["regulation"]`. Если не нашлось, повтори без
   `kinds`. Из ответа возьми **естественный ключ** документа
   (например `regulation:purchasing`), его заголовок и ревизию. Если кандидатов
   несколько, покажи их человеку и спроси, какой регламент нужен. Не выбирай за
   него.
2. **Прочитай текст по пунктам.** Вызови `cp_recall` с `anchor` — ключом
   документа и `include_pack: true`, при необходимости с большим
   `budget_tokens`. Выпиши пункты с номерами как в документе (`4`, `4.2`).
   Пункт без номера назови его заголовком — эта строка пойдёт в `section`.
   Текст пунктов не пересказывай своими словами: сохраняй их формулировки.
3. **Составь таблицу требований.**

   | Пункт | Требование (цитата, коротко) | Вид | Элемент процесса | Тест |
   |---|---|---|---|---|

   Виды требований:
   - **проверяемое** — порог, срок, кворум, запрет, обязательный шаг, порядок.
     На каждое пишется тест;
   - **процедурное** — шаг, который надо сделать, но результат не проверяется
     машинно. Шаг человека получает `governedBy`, тест проверяет, что задача
     назначена;
   - **справочное** — определения, цели, общие положения. Элемента не требует,
     в покрытии останется непокрытым; это нормально, но отметь явно.
4. **Покажи таблицу человеку.** Спорные толкования пунктов (что значит
   «незамедлительно», кто такой «ответственный») реши с ним. Дальше
   собери черновик спецификации по форме скилла `describe-process`: пункты
   шаблона, на которые регламент не отвечает (исключения, владелец, личность),
   спроси у человека.
5. **Напиши тесты раньше описания** — скилл `write-tests-first`. На каждое
   проверяемое требование нужен хотя бы один тест. В `description` теста укажи
   пункт: `description: "п. 4.2: свыше 10 млн — два согласующих"`.
6. **Опиши процесс** — скилл `author-package`. Каждый элемент, который
   исполняет пункт, получает ссылку:
   ```yaml
   governedBy: [{document: "regulation:purchasing", section: "4.2"}]
   ```
   Ссылку ставь на самом узком элементе: на строке таблицы решений, на шаге, на
   стадии. На процесс целиком ставь только документ без `section`. Элементы
   наследуют регламенты объемлющих элементов (так их показывает
   `cp_process_explain`), поэтому одну ссылку не дублируй вниз по дереву.
7. **Доведи проверку и тесты до зелёного** — скилл `validate-and-fix`.
   Предупреждение о `governedBy` на документ, которого нет в памяти, значит
   опечатку в ключе или регламент в другом workspace. Не игнорируй его.
8. **Построй план** — скилл `simulate-and-plan`. Покажи человеку раздел
   `regulationCoverage` плана ядра (секция `core` плана установки): для каждого регламента — пункты с элементами, которые
   их исполняют, и **отдельным списком непокрытые пункты**. Каждый непокрытый
   пункт объясни: «справочный» или «не реализован — нужен шаг …».

## Чек-лист

- [ ] Ключ регламента взят из ответа `cp_recall`, а не придуман.
- [ ] У каждого проверяемого требования есть тест, и в `description` теста
      назван пункт.
- [ ] Каждый шаг, стадия и строка таблицы, исполняющие пункт, имеют
      `governedBy` с `section`.
- [ ] У процесса есть `owner`: ему правило `regulation-drift` пакета
      `process-knowledge` адресует задачи, когда регламент изменится.
- [ ] В плане показаны покрытые и непокрытые пункты. Непокрытые объяснены
      человеку.

## Частые ошибки

- Пересказывать пункт своими словами в `governedBy` или в тексте формы:
  расхождение с регламентом потом не найти. Ссылка — только ключ и номер пункта.
- Ставить `section` на процесс целиком: покрытие показывает один элемент на
  все пункты.
- Порог из регламента зашит литералом в `when` шага. Пороги и уровни
  задаются строками таблицы решений со своим `governedBy`: правило
  `regulation-drift` укажет на строку таблицы, когда порог изменится.
- Считать, что покрытие — это тесты. Покрытие регламента считает ядро по
  `governedBy` и разделам документа в памяти, а покрытие тестами — отдельный
  отчёт `pkg_test`.
- Обращаться к памяти в обход ядра. Только `cp_recall`.

## Эталоны

- Процесс пакета: стадии, таблица решений `claim-route`, согласование —
  `examples/claims/claims/processes/claim.yaml` в репозитории package-sdk.
- Регламент на стадии и строке таблицы (в примере его нет):
  `tests/fixtures/process/purchase.process.yaml` (`governedBy` процесса, стадии `price`
  и таблицы `approval-level`).
- Правило сверки регламента и процесса — `regulation-drift` платформенного пакета
  `process-knowledge`: оно адресует владельцу процесса задачу, когда регламент меняется.
