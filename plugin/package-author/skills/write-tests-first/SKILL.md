# Тесты раньше описания

Тест пакета — сценарий: начальные данные, события, сдвиг виртуального времени,
завершение шагов людьми и агентами, заглушки скиллов, агентов и памяти,
ожидания. Его прогоняет ядро в песочнице тем же движком, что и живой
экземпляр. Побочных эффектов нет.

Порядок строгий: **сначала тест, потом описание**. Тест, который ни разу не
падал, ничего не доказывает.

## Правило плагина

Тесты пишутся и гоняются без стенда (`pkg_test` исполняет их кодом ядра в песочнице
и на стенд ничего не пишет). Применение
на стенде — только после показа плана и явного «да» человека (скилл
`simulate-and-plan`).

## Где лежат тесты

`<пакет>/tests/<сценарий>.test.yaml`, один сценарий на файл. Первая
строка файла — ссылка на схему тестов (путь пишет `package-sdk add process`):

```yaml
# yaml-language-server: $schema=<путь к схеме>/test.schema.json
```

Контракт — `schema/v1/test.schema.json` package-sdk. Образец —
`examples/claims/claims/tests/claim-small-refund.test.yaml` в репозитории package-sdk.
Тесты правил (`subject: rule`) и типов задач (`subject: taskType`) — скиллы `author-rule` и
`author-work`.

## Порядок

1. **Составь список сценариев** из черновика спецификации: основной путь; каждый
   исход; каждая ветка таблицы решений; каждое согласование (кворум набран,
   досрочный отказ, разделение обязанностей); каждый срок (таймер, эскалация по
   уровням); каждое исключение (отмена с компенсациями, приостановка и
   возобновление, перенос даты с пересчётом таймеров); ответы памяти (`recall`
   нашёл и не нашёл, таймаут); ошибки скиллов (повтор, `catch`). Для процесса
   по регламенту — по тесту на каждое проверяемое требование, с номером пункта
   в `description`.
2. **Если пакета нет, заведи его** с `package.yaml` (вид `Package`, версия
   `0.1.0`) — скилл `author-package`, раздел «Новый пакет». Процесса в пакете
   пока нет.
3. **Напиши тесты.** Id шагов, стадий и таблиц в тестах — это id будущего
   описания: выбери их сейчас (`[a-z][a-z0-9-]*`, стабильные — на них ссылаются
   журнал, миграции и раскладка) и держи список рядом.
4. **Проверь форму тестов без стенда:**
   `pkg_check` с `path` пакета (или `package-sdk check --package <пакет>`). Ожидаемая
   ошибка на этом шаге — «такого Process нет в пакете». Любая другая ошибка
   (схема теста, лишнее поле) — ошибка теста: исправь её.
5. **Опиши каркас процесса** (`author-package`): `start`, `data`, одна стадия с
   первым шагом. Прогони `pkg_test` по пакету.
6. **Убедись, что каждый тест падает по своей причине.** Запиши в рабочую
   таблицу: тест → шаг сценария, на котором он упал → причина. Правильная
   причина — невыполненное ожидание (`expect`) поведения, которого ещё нет, или
   ссылка на шаг, которого ещё нет. Если тест **прошёл** до описания его
   поведения, он ничего не проверяет. Усиль ожидания (`data`, `tasks`,
   `timers`, `events`, `outcome`) и прогони ещё раз.
7. **Дальше** — `author-package` и `validate-and-fix`: наращивай описание,
   пока все тесты не станут зелёными. Тест меняй, только если неверен сам
   сценарий, и скажи об этом человеку.

## Конструкции теста

```yaml
process: claim                    # ключ процесса пакета
name: возврат после согласования
description: "п. 3.1 регламента: возврат только после согласования"
given:
  clock: "2026-10-01T09:00:00+03:00"      # виртуальное «сейчас»
  principals: {claims-officer: [anna], claims-lead: [fedor, fiona]}
mocks:
  skills:
    notify.send@1: [{output: {delivered: true}}]   # выход проверяется по схеме скилла
  recall:
    - {step: recall-supplier, output: {nodes: [], edges: [], truncated: false}}
steps:
  - emit: {observation: claim.received, payload: {claim: "CL-1", amount: 120000}}
  - expect: {stages: {review: open}, tasks: [{step: review-claim, assignee: anna}]}
  - complete: {step: review-claim, by: anna, output: {verdict: ok}}
  - approve: {step: approve-refund, by: anna, decision: approve,
              expectRefused: separation_of_duties_violation}
  - approve: {step: approve-refund, by: fedor, decision: approve}
  - advance: P3D                  # или until:<id таймера>
  - expect: {events: [process.escalated]}
  - expect: {status: completed, outcome: refunded, noSideEffects: true}
```

- `emit` — событие (`event`) или наблюдение (`observation`) с `payload`.
- `advance` — сдвиг виртуального времени (ISO 8601) или `until:<таймер>`.
- `complete` — завершить шаг человека или агента (`output` проверяется по форме),
  `cancel: true` — отменить задачу.
- `approve` — голос согласующего; `expectRefused` — ожидаемый отказ ядра.
- `expect` — стадии, вехи, задачи, таймеры (`provisional` для предварительного
  календаря), данные (путь → значение), события `process.*` с прошлого
  `expect`, память (`recalled`, `remembered`), состояние сроков `sla` (id шага
  со сроком или `process` → `ok`/`warning`/`breached`/`paused`), статус, исход,
  ошибка, `noSideEffects: true`.
- `mocks.recall` — ответ памяти шагу `recall` (`step` — id шага); `timeout:
  true` — таймаут памяти; `error` — ошибка скилла в форме RFC 7807.

## Чек-лист

- [ ] Каждый сценарий черновика — отдельный тест; у каждого исхода есть тест.
- [ ] Каждый тест видели падающим по правильной причине (таблица «тест → шаг →
      причина» есть).
- [ ] В последнем `expect` основного пути стоит `noSideEffects: true`.
- [ ] Сроки проверяются через `advance`, а не через подставленные даты
      «в прошлом».
- [ ] Заглушки скиллов отвечают по схеме выхода скилла из каталога. Нарочно
      неверная заглушка — это тест на ошибку, и он ждёт ошибку.
- [ ] Разделение обязанностей проверено голосом запрещённого principal с
      `expectRefused`.

## Частые ошибки

- Писать описание процесса «чтобы посмотреть, как выйдет», а тесты потом.
- Тест, который проходит без описания поведения: в нём только `emit` и
  `expect: {status: running}`.
- Время из `now()`: в тестах его нет. «Сейчас» задаёт `given.clock`, дальше
  время двигает `advance`.
- Неверный формат даты: `clock` и даты в `payload` пишутся в RFC 3339 со
  смещением (`+03:00`), длительности — в ISO 8601 (`P3D`, `PT4H`). Годы и месяцы
  в длительностях CEL не поддерживаются.
- YAML 1.2: `on`, `off`, `yes`, `no` — строки; булевы значения только
  `true`/`false`. Номер вроде `0373100000126000001` бери в кавычки, иначе он
  станет числом.
- Заглушка без `step` у `recall`, когда шагов `recall` несколько: ответ
  достанется не тому шагу.
