# Проверка и исправление по машиночитаемым ошибкам

SDK проверяет пакет кодом ядра без стенда и отвечает находками одной формы:

```json
{"code": "unknown_data_field", "severity": "error",
 "path": "/spec/stages/1/steps/0/output/as/decison",
 "file": "processes/purchase.yaml", "line": 42,
 "message": "data has no field decison", "hint": "did you mean decision?"}
```

`pkg_check` отдаёт их в `errors` (и строки предупреждений в `warnings`), `pkg_test` — по
ступеням пирамиды (`stages[].problems` ступени `check`, итоги пакетов — `stages[].packages[]`, отчёт
сценариев — `stages[].packages[].report`).
Отказ инструмента — `{error, message, hint?}`. Читай `code`, `file`, `line` и `hint`;
`message` — пояснение.

## Правило плагина

Цикл ничего не пишет на стенде: `pkg_check` и `pkg_test` только читают
(`pkg_test` исполняет код интеграции пакета и его тесты на этой машине). Применение — только скиллом `simulate-and-plan` после
явного «да» человека.

## Порядок цикла

1. **Проверка без стенда:** `pkg_check` с `path` — каталогом пакета: схема,
   замкнутость ссылок, объявленные переменные, валидаторы ядра (код ядра — в
   package-sdk). Для тестов она же проверяет форму по `test.schema.json` и ссылки на
   шаги. `ok: false` — есть ошибки в `errors`. Ошибка «доменные валидаторы ядра не
   импортируются» — нет кода ядра: поставь package-sdk с extra `sandbox` (или,
   осознанно, `schema_only`).
2. **Проверка ядром стенда** (по желанию: роли, календари и скиллы стенда):
   `pkg_check` с `server` — одним из стендов, настроенных для сервера
   (`server_not_allowed` иначе), — и, если процессы пакета живут в workspace,
   `workspace_id`.
3. **Разбери находки.** Сначала `severity: error`, по файлу и строке сверху вниз.
   Одна причина часто даёт несколько находок: например, опечатка в поле схемы
   данных роняет все выражения, которые его читают. Исправляй причину.
4. **Исправь** операцией `package-sdk edit` (скилл `author-package`) или точечной
   правкой строки из `line`. Файл целиком не переписывай.
5. **Повтори** шаги 2–4, пока ошибок нет. Предупреждения
   (`severity: warning`) разбери все: исправь или объясни человеку, почему
   оставляешь.
6. **Тесты:** `pkg_test` с тем же `path` (`tests` — имена или файлы сценариев,
   чтобы гонять только нужные). Ступени: `check` (не прошла — выше не идут),
   `skills` (контракты скиллов кода интеграции), `integration` (pytest кода интеграции),
   `scenarios` (сценарии кодом ядра). У упавшего сценария смотри номер шага и
   ожидание, которое не выполнилось. Сценарии правил и типов задач песочнице нужна
   пустая база PostgreSQL (`PACKAGE_SDK_SANDBOX_DATABASE_URL` в окружении MCP-сервера);
   без неё они `skipped` с находкой `sandbox_database_required`, и прогон не зелёный.
7. **Реши, кто неправ: тест или описание.** По умолчанию неправо описание:
   тест написан по подтверждённой спецификации. Тест правь, только если
   неверен сам сценарий, и скажи человеку, что и почему поменял.
8. Когда тесты зелёные, посмотри **покрытие** в ответе `pkg_test`:
   непройденные элементы, переходы, строки таблиц, обработчики. Допиши тест
   (`write-tests-first`) или убери лишний элемент.
9. **Стоп-условие:** если одна и та же находка вернулась после трёх разных
   исправлений, остановись и покажи человеку находку, свои попытки и вопрос.

## Частые находки и что делать

| code | Причина | Исправление |
|---|---|---|
| `schema_violation` | форма объекта не по схеме каталога (лишнее поле, не тот вид шага) | сверить с `schema/v1/object.schema.json`; у шага ровно один вид |
| `expression_syntax_error` | синтаксис CEL (строка без кавычек CEL, `=` вместо `==`) | позиция — в `message`; строковые литералы — `"'текст'"` |
| `expression_type_error` | тип или поле не сходятся; `now()` | тип поля — из `spec.data`; время — `event.time`, `instance.clock` |
| `expression_too_complex` | длина > 4000, глубина > 32, вложенность макросов > 3 | вынести расчёт в шаг `set` |
| `unknown_data_field` | поля нет в схеме данных | добавить в `spec.data` или исправить опечатку по `hint` |
| `unwritten_data_field` | поле читается, но нигде не пишется | `set`/`output.as` раньше чтения или поле в `start.set` |
| `data_type_mismatch` | запись не того типа в поле данных | привести выражение или схему |
| `unknown_skill`, `unknown_skill_input`, `skill_input_missing`, `skill_input_type_mismatch` | скилл или его вход не по контракту из каталога | `cp_describe_skill`; добавить пакет в `requires` |
| `unknown_task_type`, `unknown_role`, `unknown_agent`, `unknown_calendar`, `unknown_artifact_type` | ссылка на объект, которого нет ни в пакете, ни в `requires`, ни в каталоге | завести объект в пакете или добавить `requires` |
| `unknown_decision_table`, `unknown_table_input`, `table_output_missing`, `unused_decision_table` | таблица и её использование не сходятся | id таблицы, входы и выходы |
| `unreachable_step`, `unreachable_stage`, `unreachable_milestone`, `dead_end` | сторожа не пускают или путь не кончается | проверить `entry`/`exit`/`when`; у процесса-цели нет `complete` — это норма, см. `goal-as-process` |
| `duplicate_element_id`, `id_pattern` | id не уникален или не `[a-z][a-z0-9-]*` | переименовать через `package-sdk edit rename` |
| `invalid_assignment`, `invalid_approval`, `invalid_escalation` | цепочка назначения, кворум или эскалация | кворум `{atLeast: N}` не больше числа кандидатов |
| `invalid_form_schema` | форма шага не JSON Schema | `package-sdk edit add-form-field` |
| `invalid_migration`, `element_removed`, `element_kind_changed` | новая версия теряет элементы старой | `migrations` с картой; см. `simulate-and-plan` |
| `governed_by_unknown_document`, `governed_by_unknown_section`, `governed_by_unchecked` | регламента или пункта нет в памяти, или память недоступна | ключ — из `cp_recall`; см. `process-from-regulation` |
| `process_owner_missing` | нет `owner` | добавить владельца по черновику |
| `process_identity_required`, `unresolved_install_variable` | нет личности процесса или переменной установки `${…}` | `identity.agent` пакета; переменная — в `.env` установки |
| `memory_case_undeclared` | `{case: true}` без `memory.case` | объявить проекцию дела |
| `invalid_yaml` | файл не разобрался (YAML 1.2) | отступы, кавычки; `on`/`yes`/`no` — строки |
| `mock_missing` (тест) | в тесте нет заглушки для вызова | добавить в `mocks` ответ по схеме |
| `package_not_found`, `package_empty` | неверный `path` | каталог с `package.yaml` (абсолютный или от корня сессии) |

## Чек-лист выхода

- [ ] `pkg_check`: `ok: true`, предупреждения разобраны.
- [ ] `pkg_test`: `status: passed`, покрытие просмотрено.
- [ ] Каждый изменённый тест согласован с человеком.

## Частые ошибки

- Чинить симптом: подавлять находку `has()` там, где поле должно быть
  обязательным в схеме данных.
- Править тест, чтобы он прошёл.
- Переписывать весь файл ради одной строки: diff плана станет нечитаемым.
- Путь к файлу, а не к каталогу пакета. Инструменты `pkg_*` читают каталог на
  диске этой машины; относительный путь — от корня сессии.
- Считать «нет кода ядра» проверкой: `schema_only` проверяет только схему и ссылки.
